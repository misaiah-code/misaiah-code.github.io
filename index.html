Professional Self-Assessment

Growth across the Computer Science program

Introduction

Completing the Computer Science program and building this ePortfolio has helped me see how much my approach to computing has changed. Earlier in the program, I often measured success by whether I could make a program run and satisfy the assignment requirements. As I progressed, I became more focused on the qualities that make a solution useful beyond the classroom: maintainability, testing, security, clear communication, appropriate data structures, and thoughtful design decisions. The capstone brought those ideas together by requiring me to return to earlier work, evaluate it using what I know now, and improve it without losing sight of its original purpose.

My professional goal is to continue developing as a software engineer who can build practical applications while treating security and reliability as part of the design rather than as afterthoughts. I value solutions that are understandable to other developers, useful to the people who depend on them, and designed with realistic constraints in mind. The portfolio demonstrates those values through work in mobile development, algorithms and data structures, full-stack development, databases, testing, and secure coding.

Collaboration and Communication

The program also showed me that computer science work is rarely only about writing code. In software-development-lifecycle coursework such as CS 250, I learned to think about development from several perspectives, including developers, testers, product owners, and end users. That changed the way I approach requirements and revisions. A technically correct solution can still be a poor solution if it does not address the actual need, if another developer cannot maintain it, or if the design cannot be explained clearly to the people making decisions about it.

Several later courses required me to communicate technical decisions to different audiences. In IT 212, for example, I developed a network proposal for a new office and had to explain choices such as topology, addressing, Internet connectivity, VPN access, bandwidth, monitoring, and security in a way that would make sense to organizational leadership. In CS 470, I worked through the migration of a full-stack application toward an AWS serverless architecture and then prepared a conference-style presentation explaining containers, Docker Compose, S3, Lambda, API Gateway, DynamoDB, elasticity, cost, and cloud security. Those experiences strengthened my ability to move between implementation details and higher-level explanations depending on the audience.

Feedback and revision have also become a normal part of my workflow. Across the program I have had to review instructor feedback, troubleshoot unexpected behavior, revise written explanations, and reconsider technical choices when an implementation did not work as expected. The capstone reinforces that process because the final ePortfolio is not simply a collection of first attempts; it is a presentation of work that has been reviewed, enhanced, and explained.

Technical Growth

My coursework gave me experience with several ways of organizing and evaluating data. Data structures and algorithms taught me to consider how storage choices affect searching, sorting, traversal, validation, and complexity. I learned that there is rarely one structure that is automatically best. A binary search tree may be useful for ordered traversal, while a hash-based structure can improve repeated direct lookup. The important skill is understanding the trade-off and selecting a structure based on the actual behavior the application needs.

My understanding of software engineering grew alongside that algorithmic foundation. CS 320 emphasized testing and quality assurance, which made me more aware that working code still needs evidence that it behaves correctly. Other development courses required me to separate responsibilities, validate input, manage application state, and consider how software will be changed later. CS 350 extended that thinking into hardware and software integration through Raspberry Pi work involving GPIO devices and state-based behavior. That project helped reinforce the value of modular logic and systematic debugging because errors could come from either software behavior or the physical system.

Database coursework also changed the way I think about application data. DAD 220 introduced relational database concepts, while later work with MongoDB and full-stack applications showed how data models, APIs, validation, and user interfaces depend on one another. CS 340 provided additional experience working with a MongoDB-backed dashboard and transforming stored data into useful filtered results and visual information. These experiences made database design feel less like a separate backend task and more like part of the overall behavior and reliability of an application.

Security Mindset

Security became one of the clearest areas of growth during the program. In CS 405, I worked with secure-coding principles such as input validation, exception handling, least privilege, defensive design, and risk-based prioritization. In earlier software-security work, I used cryptographic techniques and dependency analysis to think about both the code I wrote and the third-party components an application depends on. Rather than assuming that valid input, trusted users, or safe dependencies will always be present, I learned to consider how a system behaves when those assumptions fail.

CS 410 strengthened that mindset from another direction by requiring me to analyze compiled programs and assembly-level behavior. Reverse engineering made software failures and vulnerabilities feel more concrete because I had to look below source code and reason about control flow, memory, registers, and program behavior. Together, these courses encouraged me to treat security as a design responsibility. In my current work, that means asking whether credentials are protected, whether data is scoped to the correct user, whether input is validated at the right layer, whether failures expose unnecessary information, and whether authorization is actually enforced rather than merely intended.

Professional Growth and Portfolio Overview

The ePortfolio represents the progression from completing guided assignments to evaluating and improving my own previous work. The three artifacts were chosen because they show different parts of that growth. The Weight Tracking application focuses on software design and engineering by improving application structure, validation, testing, session handling, and protection of user data. The ABCU Advising Course Planner focuses on algorithms and data structures by combining ordered tree traversal with faster hash-based lookup, stronger parsing and validation, safer memory ownership, and explicit complexity analysis. Travlr Getaways focuses on databases through stronger schema validation, more predictable API behavior, complete CRUD support, and better protection of administrative operations.

Taken together, the artifacts show more than three isolated projects. They demonstrate a common process: understand an existing system, identify weaknesses, choose improvements that solve specific problems, test or validate those improvements, and explain the reasoning behind the final design. That process is the skill I expect to carry forward into professional software development. I am leaving the program with broader technical experience, but more importantly, with a better understanding of how to evaluate my own work, communicate technical decisions, and continue improving as technologies and requirements change.
